Telling prompts apart in the Messages panel

Recommendation: give every row in the Messages panel a kind, then add a turn outline that nests each turn under the prompt that started it (Option A below).

Today the panel colors each row by the message's stored type. The user's prompts, agent updates, slash commands, and compaction summaries are all stored as user messages, so they all get the same blue dot. In the session below, agent updates outnumber the typed prompts by more than five to one.

Data: one real Claude Code session with background agents (Fri 25 Sep to Mon 28 Sep 2026, times in Pacific). Prompts, agent names, and timestamps are real; Claude's reply text and recaps are replaced with filler, and personal identifiers are removed. Row kinds are implemented in PR #600; the rest is a proposal in issue #598.

Every mockup follows these switches: They stand in for the person and lightning buttons in the panel header. Option C keeps its own filters.

What the panel shows today

The panel on the left rebuilds today's Messages panel from this session, using the same rules as the current code. Row numbers are approximate because the real panel only numbers the rows it has loaded.

  • One dot per stored type. HighuseNavigatorEntries.ts (lines 55-58) takes each row's role straight from message.type. An agent update arrives as a user-type message, so it gets the blue user dot. This was read in the code and matched against the running app.
  • Agent previews show IDs, not names. HighThe preview strips XML tags but keeps what was inside them. An agent update therefore reads as its task ID, its tool-use ID, and an output path. The agent's name and status come later in the same message, so the two-line clamp cuts them off.
  • The person button filters on the same role. HighIt keeps every user-type row, so agent updates stay in the "user messages only" view. With both buttons on, this session once showed 51 rows: the 8 rows of the person-only view plus all 43 agent updates.
  • Row numbers count rows, not prompts. MediumIn one view of this session, the row marked #175 was the fourth prompt. The number depends on which rows happen to be loaded, so it is not a stable reference.
  • The panel only indexes loaded messages. MediumMessages load newest-first in pages of 200 (MESSAGE_PAGE_SIZE in messageSlice.ts). In this session, a list that started at 9:14 PM left out the first two prompts, at 8:20 PM and 9:10 PM.
  • "(user message)" rows are orphaned tool results. MediumThe backend merges each tool result into the tool call that produced it (merge_tool_execution_messages in multi_provider.rs). When that call sits on a page that has not loaded yet, the result arrives alone, with no text to preview. This comes from reading the code, and it fits a list that started one minute after an agent launch.

Five ways to tell them apart

Each mockup renders the same session. Click a row to select it. In Option A, click a turn to open or close it.

A

Turn outline

Recommended

Each prompt becomes a collapsible turn. The turn header counts what followed it: replies, tool calls, agents started, and agent updates. With "Prompts only" on, the panel becomes a pure outline.

Good at
It is a true outline of the session. All turns fit on one screen when closed, and agent updates fold into one row per task. The header stays pinned while you scroll inside a long turn.
Costs
It is the largest change. The list becomes a tree, which needs tree semantics for screen readers and Left and Right keys to fold turns. Fold state must survive older pages loading.
Code touched
A new hook groups entries into turns. MessageNavigator.tsx renders headers and children through the same virtualizer. MessageNavigator.accessibility.test.tsx moves from a listbox to a tree.
B

Kind glyphs

Keep the flat list, and give every kind its own icon, color, and label. Prompts get full-strength text on a tinted row, and everything else is muted.

Good at
It is the smallest change, and every other option needs its classification anyway.
Costs
The list stays flat. At several hundred rows, the shape of the session is still hard to see.
Code touched
Add a kind field in types.ts, set it in useNavigatorEntries.ts, and replace ROLE_STYLES in NavigatorEntry.tsx with per-kind styles. About nine new labels go into each of the five locales.
C

Named filter presets

Replace the two icon buttons with three named presets and one chip per kind, each with its count. This mockup keeps its own filters and ignores the switches at the top.

Good at
Nothing needs a tooltip to decode. The counts alone tell you that this session is mostly agent traffic.
Costs
It takes about 60 px of height, and the chips wrap onto more lines in a narrow panel.
Code touched
The header in MessageNavigator.tsx changes. A set of visible kinds joins filterSlice.ts and persists the way messageFilter already does.
D

Size tiers

Keep one chronological list but vary the visual weight. Prompts are cards, work is one-line rows, back-to-back agent updates merge into chips, and long gaps get a divider.

Good at
Prompts stand out while you scroll fast, and the surrounding context stays in place.
Costs
Row heights vary more, so the height estimate in MessageNavigator.tsx (estimateSize) needs a value per row variant.
Code touched
The kind classification from Option B, plus row variants, merge logic for update chips, and gap dividers.
E

Agent lanes

A narrow gutter draws a lane for you, one for Claude, and one per running agent. An agent's bar runs from its launch to its last update, so overlapping bars show parallel work.

Good at
It is the only option that shows parallelism. You can see three batches running at once and when each one finished.
Costs
The gutter takes about 90 px of a narrow panel. Many concurrent agents crowd the lanes, and a screen reader cannot get the meaning the drawing carries.
Code touched
Compute each task's span from launch to last update, assign lanes, and draw the gutter for each row.

Smaller fixes that help every option

Name the agent in its update

The notification already carries a summary and a status. Reading those fields instead of stripping tags turns an ID string into a sentence.

Group updates per task

TaskTypeUpdatesLast

Mark long gaps

This session spans three days. A divider for any pause over two hours shows where you stepped away, which is also where a new line of work usually starts.

    Say when earlier messages are not loaded

    Each page response carries total_count, so the panel knows how many messages it has not loaded yet. A top row can say so and offer to load them, instead of silently starting at row #1.

    Jump between prompts from the keyboard

    The app has two global shortcuts today: Ctrl+K for search and Ctrl+Shift+M for this panel (useAppKeyboard.ts). A pair such as Alt+↑ and Alt+↓ could move the main view to the previous or next prompt. That works even with the panel closed.

    Remember the switches

    The person and lightning buttons reset every time the app restarts. Their defaults live in initialFilterState in filterSlice.ts, with no storage behind them. The main view's message filter in the same file already persists to localStorage, so the pattern exists.

    Recommended order

    Each step is useful on its own, and each one makes the next step smaller.

    1. Classify rows by kind (Option B's data model). Implemented in PR #600: a shared classifier, an icon per kind, readable agent updates, and a person button that keeps typed prompts and slash commands.
    2. Add a prompt-jump shortcut. Alt+Up and Alt+Down move the main view to the previous or next prompt, even with the panel closed.
    3. Add the turn outline (Option A). A list-or-outline switch in the panel header keeps the flat list available. The outline should highlight the turn in view and say when earlier messages are not loaded.
    4. Consider lanes (Option E) later, perhaps only inside an open turn that started two or more agents.

    Named presets (Option C) become unnecessary once the outline exists. Closing every turn does the person button's job, and grouping updates per task does the lightning button's.

    Other providers need their own rules. Codex, Gemini, OpenCode, and others record agents differently, and messageCategories.ts already detects each one's parallel-agent calls. The classifier should reuse that code instead of matching Claude Code's tags alone.
